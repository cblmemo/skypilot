⏺ Summary of 9935 analysis + fix

  9935's new failure mode (different from the previous 3):
  - Recovery was verified (14 → 18/30), but then the job stayed at 18/30 RUNNING
   for the full 60-minute test step timeout. 20 batch output files existed on S3
   but DB only showed 18 → workers were doing work that the coordinator never
  got credit for.

  Root cause (most likely): After _shutdown_stale_workers sends sdk.cancel, the
  old worker service hasn't fully released port 8290 yet. The new worker service
   sdk.exec starts, its Python HTTP server tries to bind 8290, fails with
  EADDRINUSE, and exits. The _launch_worker_service health probe however hits
  the still-running OLD service and sees 200, so the coordinator thinks it's
  fine and dispatches — but subsequent sdk.exec worker-service launches keep
  colliding on port. Net effect: coordinator spins without making progress, job
  stays RUNNING until the test gives up.

  Changes (sky/batch/{constants,coordinator}.py + 
  tests/smoke_tests/test_batch.py):

  1. STALE_WORKER_GRACE_PERIOD = 15 — after _shutdown_stale_workers cancels,
  sleep 15s so SIGTERM'd processes actually die before we spawn replacements.
  2. Worker startup preamble — before starting the Python HTTP server, fuser 
  -k/lsof kills any lingering holder of port 8290 and waits up to 10s for the
  port to be free. This guarantees forward progress even when the cancellation
  raced.

  Just queried the pod directly:

  - managed_jobs DB: one row, job_id=1, job_name='sky-batch-e2fb',
  pool='test-batch-pool'
  - Recovery file on disk: sky_job_2 (and previously sky_job_1 for the pool's

  - Content of sky_job_2: mkdir -p ~/sky_logs/2-sky-batch-e2fb/run.log …

  So sky_job_2 is the recovery script for the managed batch job whose
  managed_job_id=1. They are not the same number.

  Why "job 2 should still be recovered" doesn't work under the old filter

  The filter logic was:

  ALL_IN_PROGRESS_JOBS = {managed_job_id for mj in managed_jobs if not
  DONE/WAITING}  # → {1}
  for sky_job_N:
      if N not in ALL_IN_PROGRESS_JOBS: continue  # 2 ∉ {1} → SKIP

  Walk through it with the actual data:
  - sky_job_1 (cluster_job_id=1 = pool's serve controller): 1 ∈ {1} → RUN. This
  is the wrong thing — the filter ran the pool controller because its
  cluster-side id coincidentally matched a managed_job_id.
  - sky_job_2 (cluster_job_id=2 = managed job 1's controller): 2 ∉ {1} → SKIP.
  This is the script we actually needed to restart the managed-job controller,
  and it got dropped.

  That's exactly what I saw in my earlier failed local runs (test stuck at
  "Progress after recovery: 9/30" for 60 min): the managed-job controller never
  respawned because its recovery script was filtered out.

  Why the "targeted" filter I wrote first doesn't fix it

  I tried to make it smarter by also including pool serve controllers'
  controller_job_id in the set. That gives {managed_job_id=1, 
  pool_controller_job_id=1} = {1}. Still doesn't contain 2, so sky_job_2 is
  still skipped. The missing piece is a way to go from managed_job_id → the
  cluster-side ray job id of its controller — and there is no such column in 
  managed_jobs (only controller_pid, which is a Unix PID).

  Why I went back to "run all"

  Given the DB doesn't record the cluster-side ray job id for managed-job
  controllers, the filter cannot be made correct without either:
  1. adding that column (DB migration + changes in the launch path), or
  2. parsing each sky_job_N file's task-name to classify it (fragile), or
  3. dropping the filter.

  The recovery scripts themselves are idempotent — they check state and bail on
  terminal jobs — so option 3 is safe but slightly wasteful. The template's own
  TODO already flags "this may run a lot of things … we should do more tests and
   make sure it will scale well", so we were already aware this path runs
  multiple scripts.

  My latest edit keeps the IS_SKYPILOT_JOB_CONTROLLER env-var detection (still
  based on "any managed jobs in DB?") but runs every sky_job_N unconditionally.
  If you'd rather pursue option 1 (add controller_ray_job_id to job_info), I can
   do that instead — it's the only way to keep the filter without guessing.
